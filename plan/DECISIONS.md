# Decisions, interfaces and decision rules

Every decision has an ID `D-###`. Part 1 holds process and scope decisions, Part 2 the design, Part 3 the public interfaces, Part 4 the decision rules (`DR-##`) the implementer applies at a fork. Claims `C-###` are in `research/claims.json`; assumptions `A-###` in `plan/ASSUMPTIONS.md`; risks `R-###` in `premortem/RISK_REGISTER.md`; tests `T-###` in `tests/` and `plan/TRACEABILITY.md`.

Terms used throughout:

- **Core**: the C++ library `folkdsp` under `core/`, which contains all sound generation and has no dependency on JUCE.
- **Wrapper**: the JUCE code under `plugins/common/` that turns the core into a VST3 plugin and a standalone program.
- **Render tool**: the command-line program `folk-render` under `tools/folk-render/`, which drives the core from an event file and writes a WAV file. All audio tests go through it.
- **Preset data**: the tables of physical and tuning values in `presets/*.json`, each value carrying the claim it comes from and a confidence. Code reads them at build time (they are compiled in as generated headers by `tools/gen_presets.py`).
- **Reed**: one free-reed tongue with its cell. **Rank**: one full set of accordion reeds at one pitch level. **Course**: two strings played as one.

## Part 1. Process and scope

**D-001 Unreachable hosts (0.1).** The planning sandbox reaches package registries, public git over the git protocol, and the hosts the owner added to the environment's allowlist on 2026-11-14 (recorded in `research/rounds/round-1.md`). It does not reach `pubs.aip.org`, `www.mdpi.com` or `freesound.org` (HTTP 403 to automated requests), nor release downloads of repositories outside the session. Alternative channels: papers on those hosts are read from open author copies where they exist and are otherwise recorded as unread (A-012); dependencies are fetched by git at a pinned commit; release binaries (pluginval) are downloaded in CI, where their SHA-256 is checked before use. The implementer's sandbox may differ: `S-000` re-probes.

**D-002 Scope reductions.** (a) The accordion models the treble side only (ranks L, M-, M, M+, H); the Stradella bass side is not modelled. A MIDI keyboard plays single notes and the register switch selects the ranks. (b) The chromatic harmonica is the 12-hole instrument in C (C4 to C-sharp 7). (c) The melodion's bass range is a design value (C-024). (d) The input file's artefacts "slide-gap hiss", "sticky valves" and "valve buzz" are reduced to one `valve_buzz` control and the `airtightness` control; "moisture" is one control on the melodion. Reason: none of these has a source above Tier 4 (C-025, C-014 note), and each adds a control the listening gate must judge.

**D-003 Planning artifacts on the default branch (3.12).** Travel to `main` with the implementation: `HANDOFF.md`, `plan/`, `tests/`, `scripts/`, `EXECUTION_LOG.md`, `DEVIATIONS.md`, `reviews/`, `GATE-*.md`, `references/` (link records only). Stay on the generation and implementation branches only: `research/`, `premortem/`, `.checkpoints/`, `lessons/`, `knowledge/`, `RETROSPECTIVE.md`. `S-INTEGRATE` removes the second group from the pull-request branch in one commit made on a branch cut for the pull request (`pr-<run_id>`), so `impl-<run_id>` keeps everything. The pull request carries the records as they stand at `S-INTEGRATE`; the later records (log lines of `S-INTEGRATE` to `S-KNOW`, `GATE-G-003.md`, bundles) stay on `impl-<run_id>` only, and the pull request is not refreshed for them.

**D-004 No mutation-testing step.** The optional mutation-testing step of the planning protocol is omitted. Reasons: (a) the correctness gates of this plan are behavioural audio tests through the render tool, reference metrics and listening gates, and Mull instruments C++ unit-test executables, which here cover only the closed-form helpers (tuning tables and string formulas, about 300 lines); (b) no code exists at planning time, so the measured baseline, mutant count and runtime estimate that the protocol requires for a mutation step cannot be recorded honestly. The adversarial review step `S-ADVERSARIAL` is told to try hand-made mutants of the formulas instead (plan step text).

**D-005 CI platform extras (3.9.3).** Supported platforms (A-005): Windows x64, macOS arm64 and x86_64, Linux x64. Waived: an ARM64 Linux job (the plugins are not offered for ARM Linux); a libc-variant job (JUCE does not support musl; the plugins target glibc desktops); an oldest-toolchain job (the supported toolchains are exactly those of the pinned runner images, recorded per run in the job log; a hobby project makes no promise for older ones).

**D-006 Integration route.** `pull-request` (A-002). The default branch `main` exists (commit `375f650`). It has no branch protection at planning time (a new repository); `S-000` reads the protection state again and `S-INTEGRATE` waits for whatever checks are required then, and in any case for every job of `ci.yml`.

**D-007 Release.** Nothing is released (A-018). CI uploads plugin binaries as workflow artifacts with `retention-days: 3`, with the `LICENSE` file inside each archive; because the repository's visibility could not be read at planning time, the plan treats them as public distribution under AGPL-3.0, which the complete source in the same repository satisfies (C-044). Any tagged release, installer or upload elsewhere needs gate `G-002`.

## Part 2. Design

### 2.1 Free reeds (harmonica, accordion, melodion)

**D-010 Reed model.** Each sounding reed is the minimal model of C-001, one state vector `(x, v, p1, u)`:

- `x` (m): height of the tongue tip above the plate's upper face (positive on the supply side); `v = dx/dt`.
- `p1` (Pa): over-pressure in the reed cell; `u` (m3/s): volume flow from the cell through the inlet passage to the reed.
- Supply: a reservoir at over-pressure `p0` (bellows, mouth or plenum) feeds the cell through an inlet orifice of area `A_in`: `u0 = alpha * A_in * sign(p0 - p1) * sqrt(2 |p0 - p1| / rho)`.
- Cell: `dp1/dt = (rho * c0^2 / V1) * (u0 - u)`.
- Passage: `du/dt = (S2 / (rho * L2)) * (p1 - p2)`.
- Jet: `vj = (u + Sr * v) / (alpha * Su(x))`, `p2 = (rho / 2) * vj * |vj|`.
- Reed: `dv/dt = -(w0 / Q) * v - w0^2 * (x - x0) - mu * p2`, `mu = Sr * w0^2 / K`.
- Useful section `Su(x)`: the Debut/Millot law as coded in `research/spikes/s03-reed-minimal-model/reed_sim.py` (front area plus two side areas, zero local opening while the tongue is inside the plate thickness), tabulated per reed exactly as `table()` in `research/spikes/s12-reed-similarity-scaling/similarity.py` does: 2048 points over `x` in [-(6 x0 + es + er), +6 x0], linear interpolation, and the end values held beyond the ends (the reed travels to about -6.8 x0 and +7.6 x0 at 1500 Pa, so the ends are reached in normal playing; the spike is the reference for this behaviour). The table is stored in normalised units (`Su * k` against `x / x0`, which under D-012 depend only on the curve factors at that note) and built in `prepare()` for every MIDI note from 28 to 112 of the instrument (85 x 2048 values), never on the audio thread; a reed uses the table of the note it was started on, and a pitch glide (D-022, D-033) changes only its scaling `k`, not its table.
- Constants: `rho = 1.2`, `c0 = 343`, `alpha = 0.61`.
- Reference parameter set (C-001, a harmonica reed at 444 Hz): `Lr = 12.95 mm`, `Wr = 2.1 mm`, `er = 0.110 mm`, `es = 0.900 mm`, `x0 = 0.528 mm`, `hmin = 0.050 mm`, `K = 47.9 N/m`, `Q = 95`, `Sr = Wr * Lr * 0.3915`, `S2 = 25 mm2`, `L2 = 20 mm`, `V1 = 800 mm2 * 60 mm`, `A_in = 30 mm2`.

The model was run from a pressure supply in spike S03c (C-053) and re-run by a reviewer at several rates and with a second integrator (C-001).

**D-011 Integration.** Semi-implicit Euler in the order of the spike (`p1`, `u`, then `v`, then `x`), in double precision. The base rate is `R = 4` times the host sample rate. Each reed takes `m = ceil(C * f_r / (R * fs))` (recomputed whenever `f_r` changes: bend, `a4_hz`, vibrato range) equal sub-steps per base-rate sample, with `C = 110` while all three curves of D-012 equal 1 and `C = 160` as soon as any of them differs from 1 (C-060, C-063: with reference proportions 100 or fewer steps per period diverge at the highest pressure; factors on `Q` and `x0` above 1 need about 135). The source sample of a reed at base-rate sample `k` is `(u[k] - u[k-1]) * R * fs`, where `u[k]` is the flow after the last sub-step of that sample (the time derivative of D-013 as a first difference). All reeds of an instrument are summed at the base rate and decimated once per instrument by two stages, each a 63-tap linear-phase half-band FIR from `scipy.signal.firwin(63, 0.5, window=('kaiser', 8.6))` (86 dB above 0.6 of the stage's Nyquist frequency, checked at planning; coefficients generated into the preset header by `tools/gen_presets.py`). Its latency is 23.25 host samples; the engine reports 23 through `latencySamples()` (D-090) and the wrapper passes it to the host. The reed states are reset to rest (`x = x0`, others 0) at note-on.

**D-012 Scaling a reed to a pitch.** Every reed is the reference reed scaled by similarity (C-059). For a reed whose natural frequency is `f_r`, with `k = f_r / 444`: `x0`, `hmin`, `er`, `es` and `Sr` are the reference values divided by `k`; `A_in` is divided by `k`; `V1` by `k^2`; `K`, `Q`, `Lr`, `Wr`, `S2`, `L2` are unchanged. Written in the variables `x / x0` and `w0 * t` the equations are then the same for every reed, so every reed starts at the same pressure, sounds the same number of cents below its natural frequency and has the same spectrum relative to its fundamental (spike S12, 55 Hz to 5.3 kHz). Scaling the reed like a real cantilever was tried by a reviewer and fails (C-053). The similarity law makes all reeds of a rank sound alike; the differences a real instrument shows along its keyboard are introduced only by step `S-330` under rule DR-07, through three per-instrument curves over pitch stored in `presets/reeds.json`: a factor on `Q` (0.5 to 2), a factor on `x0` (0.75 to 1.5) and a factor on `hmin` (1 to 2), each a piecewise-linear function of MIDI note with at most 6 points, all equal to 1 until calibrated. The ranges are those inside which reviewers' runs stayed stable with `C = 160` and the reed still started from rest (C-063); wider factors diverged, choked or failed to start. A calibrated set of curves is accepted only if the **calibrated-set check** passes: at the 12 check pitches of rule DR-03 and both host rates, the C++ reed (run with the `reed_probe` program of step `S-200`) is silent at 28 Pa, sounds from rest at 156 Pa, 400 Pa, 1500 Pa and 1800 Pa, and no state becomes non-finite. That check sets no pitch-offset targets: the offsets of a calibrated set differ from the reference reed's and are absorbed by `tools/calibrate_reeds.py` (D-016). Under this law the source signal `du/dt` has the same level at every pitch (C-061).

**D-013 Radiated sound.** The source signal of a reed is the time derivative of its total flow `u` (a simple source radiates as the derivative of volume flow). The literature attributes the far field of an accordion reed mainly to a dipole (C-009, abstract only); that is not modelled. The sum of the reeds passes through the instrument's body filter (D-024, D-032, D-040), a per-instrument output gain `G_out`, and the limiter of D-015. The `level` parameter is a gain of `level / 0.7` applied after `G_out` and before the limiter (so the default 0.7 is unity). `G_out` is set by `tools/calibrate_gains.py --instrument <name> --render <folk-render>` (procedure GAIN of `plan/PLAN.md`: the new value is the current `presets/gains.json` value times target over measured peak, then the header is regenerated, the core rebuilt and the peak re-measured) so that a default note (harmonica MIDI 72, accordion and melodion 69, mandolin 69, bouzouki 62, 2 s long) at velocity 0.8 peaks at -12 dBFS before the limiter: the tool renders that note with `folk-render` at `level=0.007` (where `tanh` is linear to better than 0.01 %), multiplies the peak by 100, and scales `G_out` to the target; it is stored in `presets/gains.json`. The tool is written in step `S-200` and run by each instrument's step as soon as that instrument makes sound; until then `G_out` is 1.

**D-014 Oversampling, polyphony and cost.** `R = 4` with the sub-steps of D-011. Spike S05b (C-054) measured 64 sounding reeds at 4 x 48 kHz rendering 5.6 times faster than real time on the planning sandbox, reeds only. Polyphony limits (voices are stolen oldest-first beyond them): accordion 16 keys (up to 64 reeds in the Master register), melodion 10 keys, harmonica 4 notes. The target of A-009 is tested by T-013 on the Linux x64 CI runner; DR-06 covers a miss.

**D-015 Real-time safety.** No allocation, lock or system call in any method the audio thread calls (T-011). The state variables `v`, `p1`, `u` and the deviation `x - x0` are set to zero (that is, `x` to `x0`) when their magnitude falls below 1e-20, and a silent voice is switched off; the wrapper additionally enables flush-to-zero with `juce::ScopedNoDenormals`. The division by `alpha * Su(x)` uses the floored table. A confining spring of stiffness `100 * K` (`K` the reed's stiffness of D-010 as scaled by D-012) acts only on the part of `|x - x0|` beyond `20 x0`, which normal playing never reaches (a spring nearer than that changes the pitch by hundreds of cents). Parameters that change the structure of a voice (`register`, `variant`, `range`, `body`, `key`) switch between data built in `prepare()` and never allocate. If any state becomes non-finite the voice is reset and stays silent until its next note-on. The last stage of every instrument is the limiter `y = tanh(s)`: unity gain for small signals, a default note at -12 dBFS (D-013) is reduced by 0.2 dB and a note 6 dB louder by under 1 dB (so the 18 to 19 dB that the reed's level spans between breath 0.25 and 1.0 survives, T-102), and nothing can exceed full scale (T-009). The output is mono: the right channel equals the left.

**D-016 Breath, bellows and tuning.** A breath value `b` in [0, 1] comes from the note velocity (`breath_source` 0), CC 2 (1) or CC 11 (2), is smoothed with a 15 ms one-pole filter (which starts from 0 at each note-on when the breath comes from the velocity), and sets the reservoir pressure `p0 = 1250 Pa * b^1.5` (b = 0.25 gives 156 Pa, above the model's onset from rest at 100 Pa; b = 0.02 gives 3.5 Pa, below it; with full vibrato the pressure peaks at 1500 Pa, the highest pressure at which the model was verified, C-053, C-059). Because a sounding reed keeps sounding below its onset pressure (C-002), tests of the threshold start from rest. The time a reed takes to speak scales with its period (C-062: half level after about 80 ms at 440 Hz and breath 0.6, about 180 ms at breath 0.3; four times longer two octaves down), which is the model's behaviour and is left as it is. Vibrato multiplies `p0` by `1 + 0.2 * depth * sin(2 pi rate t)`, with `depth = clamp(vibrato_depth + CC 1, 0, 1)`. Tuning: the model sounds 19 to 25 cents below a reed's natural frequency, depending on pressure (most near 700 to 1000 Pa) and, under D-012, by the same amount at every pitch for the same number of steps per period (C-059). `tools/calibrate_reeds.py` (step `S-201`) runs the engine's own reed code offline at `b = 0.6` (581 Pa) and at host rates 44100, 48000, 88200 and 96000 for every MIDI note from 28 to 112 (every pitch any key of any reed instrument can sound) with the current curves of D-012 and writes, per instrument and host rate, the offset `sounding minus natural` in cents (negative, about -23) to `presets/reeds.json`; at another host rate the engine uses the table of the nearest listed rate; the engine sets `f_r = f_target * 2^(-offset/1200)` (so the natural frequency lies about 23 cents above the target). The tool is re-run whenever a curve of D-012 or the sample-rate handling changes, and `S-300` checks that the committed table matches a fresh run. Pitch then drifts with breath as the model dictates (T-103). **Note-off and voices:** a note-off sets that note's breath target to 0 through the same 15 ms filter, and the reeds fall silent by themselves (T-106); a voice is freed when the RMS of its source over the last 10 ms is 100 dB below `S_ref`, or 2 s after note-off. A note-on for a key whose voice is still sounding raises its breath target without resetting the reeds; a note-on for a free voice resets its reeds to rest. A stolen voice is faded out over 5 ms before it is reset for the new note. The **reference source RMS** `S_ref` is the RMS of the source signal (D-011, before decimation) of the reference reed (444 Hz, all curves 1) at `b = 0.6` over the last 30 % of a `reed_probe` run; under D-012 it is the same at every pitch (C-061). `tools/calibrate_reeds.py` takes it from the `source_rms` key of `reed_probe` (S-200) and stores it in `presets/reeds.json` as `source_rms_ref`. **Breath noise:** `air_noise` adds Gaussian noise (seeded per voice, reseeded by `reset()`), band-passed between 300 Hz and 8 kHz (second-order Butterworth band-pass), with RMS equal to `0.03 * air_noise * (vj_mean / 31 m/s)^3` times `S_ref`, where `vj_mean` is the jet velocity of the voice's first reed averaged over 1 ms (31 m/s is the jet velocity at 581 Pa); the noise is added to the voice's source signal at the base rate.

### 2.2 Harmonica

**D-020 Keys.** `key` 0 to 11 is C to B. Keys C to F-sharp (0 to 6) have hole 1 blow at MIDI `60 + key`; keys G to B (7 to 11) at MIDI `48 + key` (C-011: instruments labelled G to B start below middle C). The layout is the Richter table of C-011, transposed.

**D-021 Playing a MIDI note on a diatonic.** `diatonicNoteFor(key, note)` decides, in this order: (1) a natural note: the first match scanning holes 1 to 10, blow before draw; (2) a bend: the first match scanning holes 1 to 10, draw bends (depths 1 to `diatonicMaxBend`) before blow bends; (3) an overbend: an overblow on holes 1, 4, 5, 6 (one semitone above the draw note) or an overdraw on holes 7, 9, 10 (one semitone above the blow note); otherwise the note is not playable and makes no sound. Maximum bends (semitones): draw holes 1 to 6: 1, 2, 3, 1, 0, 1; blow holes 8 to 10: 1, 1, 2; all others 0 (C-012). On a C instrument this covers every semitone from C4 (60) to D-flat 7 (97). The pitch wheel below centre bends a natural note down by `wheel * maxBend` semitones; above centre it does nothing. The table is preset data (`presets/harmonica.json`), single-source (R-001).

**D-022 How a bend sounds.** Baseline (required): a bent or overbent note is played by one reed whose natural frequency is moved to the target pitch (through the calibration of D-016) and whose cell is the cell of the reed that physically sounds: for bends deeper than half the interval to the lower reed, and for every overbend, the cell and geometry are those of the other reed of the hole. During a wheel movement the natural frequency glides and the cell parameters cross-fade over 30 ms. Optional (step `S-212`, rule DR-04): a two-reed channel with a tunable upstream resonator, in which the bend emerges from the model (C-013). It replaces the baseline only if it passes every harmonica test.

**D-023 Chromatic.** `variant` 1 is a 12-hole solo-tuned instrument in C: per group of four holes, blow C E G C and draw D F A B, each group an octave above the last, hole 1 blow at MIDI 60; the slide raises a note by one semitone. `chromaticNoteFor(note)` scans holes 1 to 12 and, within a hole, blow slide-out, draw slide-out, blow slide-in, draw slide-in; the first match plays. Range MIDI 60 to 97. The wheel bends any note down by at most one semitone (C-014). `key` is ignored.

**D-024 Harmonica tone controls (design values).** `wah` moves a one-pole low-pass on the output from 6 kHz (0, hands open) to 900 Hz (1, hands closed). `air_noise` is the breath noise of D-016. `airtightness` below 1 leaks a share `(1 - airtightness) * 0.5` of the supply flow past the reed and raises the air noise by the same share. `valve_buzz` (chromatic only) adds a 150 Hz to 400 Hz amplitude flutter of depth `0.3 * valve_buzz` during the first 80 ms of a note.

### 2.3 Accordion

**D-030 Registers.** `register` 0 to 11 selects ranks, in this order: 0 Piccolo (H), 1 Clarinet (M), 2 Bassoon (L), 3 Oboe (M, H), 4 Violin (M, M+), 5 Musette (imitation) (M, M+, H), 6 Musette (authentic) (M-, M, M+), 7 Organ (L, H), 8 Harmonium (L, M, H), 9 Bandoneon (L, M), 10 Accordion (L, M, M+), 11 Master (L, M, M+, H) (C-017; names are labels, R-001). L sounds an octave below the key, H an octave above. The keys are MIDI 40 to 100; other notes are silent; so every rank stays within MIDI 28 to 112.

**D-031 Tremolo.** `musette_cents` (0 to 25, default 15) is the offset of M+ above and M- below M at A4. `musette_scaling` 0 keeps the offset constant in cents on every key; 1 keeps the beat rate in hertz equal on every key to the rate at A4, `440 * (2^(c/1200) - 1)` (C-018). The offset is applied to the calibrated sounding pitch (D-016), not to the natural frequency, so the beat rate is exact at `b = 0.6`.

**D-032 Cassotto and sordina (design values, C-019).** `cassotto` 1 routes ranks L and M (not M-, M+ or H, which stay outside the chamber) through a filter: a peaking boost of 3 dB at 700 Hz (Q 0.9) followed by a high shelf of -9 dB with corner 1.6 kHz. `sordina` 1 adds a high shelf of -8 dB with corner 1.2 kHz on every rank. All shelves and peaks in this plan are the second-order 'Audio EQ Cookbook' (R. Bristow-Johnson) biquads with shelf slope `S = 1`, as coded in `research/spikes/s18-plenum-filters/plenum.py` (`shelf`, `peak`). On a reed's source signal the cassotto lowers the energy between 2 and 10 kHz relative to the whole by 7.0 dB and the sordina by 4.4 dB (spike S18; T-122 needs 3 dB). Both are judged at the listening gate.

**D-033 Bend.** The pitch wheel below centre lowers every rank by `wheel * bend_cents` cents (0 to 25, default 25; C-020), by moving the natural frequencies, and lowers the level by `3 dB * |wheel|`.

**Key noise.** `key_noise` adds a 15 ms noise burst (Gaussian noise through a second-order Butterworth band-pass 300 Hz to 3 kHz, shaped by a 15 ms Hann window) at note-on with RMS over the burst `0.1 * key_noise * S_ref`, and at note-off one with half that RMS, seeded per note for determinism; it is added to the voice's source signal at the base rate like the breath noise of D-016.

### 2.4 Melodion

**D-040 Ranges and bodies (design values except where C-024 applies).** `range` 0: 32 keys, MIDI 53 to 84 (F3 to C6); 1: 37 keys, 53 to 89 (F3 to F6); 2: bass, 24 keys, 41 to 64 (F2 to E4, not confirmed by a maker's figure). Notes outside the range are silent. `body` 0 plastic: no filter; 1 wood: high shelf -5 dB, corner 2 kHz; 2 metal (Accordina): high shelf +3 dB, corner 3 kHz (cookbook biquads, D-032). On an A4 reed the wood body lowers the spectral centroid by 31 % and the metal body raises it by 28 % (spike S18; T-134 needs 5 % and 3 %). `moisture` scales `Q` of every reed by `1 - 0.9 * moisture` and adds `moisture * 0.4 * x0` to `hmin`. Because the useful-section table depends on `hmin` and is built only in `prepare()` (D-010), the melodion builds it there for the five moisture levels 0, 0.25, 0.5, 0.75 and 1; a note-on uses the table of the level nearest the current `moisture`, and a change of `moisture` reaches a sounding reed's `hmin` only at its next note-on (its `Q` changes at once).

**D-041 Plenum.** All open reeds draw from one volume `Vp = 200 cm3` at pressure `pp`: `dpp/dt = (rho c0^2 / Vp) * (ub - sum of the reeds' inlet flows)`. `breath_mode` 0 (pressure-controlled): `ub` is whatever holds `pp` at `p0` of D-016 (the plenum is a pressure source). `breath_mode` 1 (flow-limited): the breath reaches the plenum through the mouthpiece, an orifice of `A_m = 40 mm2`: `ub = alpha * A_m * sign(p0 - pp) * sqrt(2 |p0 - pp| / rho)`, so the plenum pressure, and with it every reed's level, falls as more keys open. Spike S18 (C-065): at velocity 0.7 the A4 reed's level falls by 2.9 dB with four keys and a further 2.3 dB with eight, and it still sounds (plenum 274 Pa) (T-131 needs 1.5 dB each). Each open key's reed draws from the plenum through its own inlet `A_in` of D-012; a closed key draws nothing. The breath `b` that sets `p0` for the plenum is that of the most recent note-on (or the controller, D-016).

### 2.5 Plucked strings (mandolin, bouzouki)

**D-060 String model.** The reference for D-060 to D-064 is `research/spikes/s17-string-body/pluck_ref.py` (`String`, `pair_partials`, `bridge_terms`, `render`, `Y_ref_for`): where this text and the spike differ, the spike is right, apart from the parameters that the spike takes as arguments. Each string is a set of partials `n = 1 .. N` with frequencies `f_n = f_1 * n * sqrt((1 + B n^2) / (1 + B))`, where `f_1` is the target pitch of the fretted note (equal-tempered, plus `pair_detune_cents` for the second string of a unison course, plus the pitch wheel) and `B = pi^3 E d^4 / (64 T L_f^2)` (C-026) uses the core diameter `d`, the tension `T = mu (2 L f_open)^2` and the fretted length `L_f = L / 2^(fret/12)`. `N` is the number of partials below 18 kHz, at most 80, fixed at the stroke; at each control tick a partial whose current (bent) frequency is above `min(18 kHz, 0.45 fs)` is set to zero, so the pitch wheel never folds partials back below Nyquist (R-040). Each partial is one complex amplitude `a` with `da/dt = i * lambda * a`. `E = 200 GPa`, steel density 7850 kg/m3.

**D-061 Losses.** The intrinsic loss factor of partial `n` is `eta_i = eta_air + eta_bend + damping * 2e-3`, with `eta_air` (outer diameter) and `eta_bend` (core diameter, fretted length, `eta_E = 1e-3` for plain and `4e-3` for wound strings) as in C-027. The bridge loss comes from the body (D-062, D-064).

**D-062 A course as coupled pairs.** *Pairing:* the partials of the two strings of a course are matched greedily by increasing distance in cents, only pairs within 60 cents, each partial used at most once, ties going to the lower partial of the first string; pairing is decided when a stroke starts and is kept until the next stroke (no cross-fade). In an octave course this pairs partial `m` of the high string with partial `2m` of the low string (C-042). *Bridge terms:* for partial `n` of string `j` with fundamental `f1_j` and wave admittance `Y0_j = 1 / sqrt(T_j mu_j)`, `z_j = i * 2 * f1_j * Y(f_jn) / Y0_j`, where `Y` is the body admittance of D-064 at that partial's own frequency; if `eta_b = 2 Re(Y) / (pi n Y0_j)` would exceed `8e-3`, `Y` is scaled down so that it equals `8e-3` (a partial landing on a body mode would otherwise die in milliseconds). *Pitch compensation:* a single partial's angular frequency in its matrix is `w - Re(z)` instead of `w`, and a paired partial's is `w - Re(z_j) - Re(z_12)`, so that a single string's mode and the in-phase mode of a unison pair sound at the target frequency (spike S17: every fretted note of the f-hole mandolin within 0.51 cents, T-140, T-154). *Dynamics:* a pair is the block `Omega = [[d1 (1 + i eta1/2) + z_1, z_12], [z_12, d2 (1 + i eta2/2) + z_2]]` with `z_12 = sqrt(z_1 z_2)`; a single partial is `lambda = d (1 + i eta/2) + z`. Each is advanced per sample by its exact one-sample propagator `exp(i Omega / fs)` (C-028, C-031), computed when a stroke starts and again on a control tick of 64 samples counted from `reset()` when the pitch wheel, `body_coupling` or `damping` changed. The pair is not expanded into eigenmodes. `course_mode` 1 plays only the first string of each course. Only the polarisation normal to the soundboard is modelled.

**D-063 Pluck (partly a design assumption).** A stroke adds to partial `n` of a string the amplitude `A * sin(n pi beta) / n * exp(-n * 0.15 * (1 - pick_stiffness)) * exp(-n * 0.1 * (1 - velocity))`, with `beta = pick_position` measured from the bridge and `A = velocity^1.5` (the force form of C-030; the two exponential factors are the assumed low-pass effect of a soft plectrum and a soft stroke). The second string of the course is struck `0.15 ms * (1.5 - velocity)` after the first with 0.9 of its amplitude; `octave_order` 1 on the bouzouki swaps the order. (A stagger of 0.84 ms, tried first, starts the strings of the E course almost in antiphase and removes the two-stage decay; spike S17.) Before a stroke, the amplitudes already on that course are multiplied by 0.15 (the plectrum touches the strings); if the new note differs from the course's current note, those remaining amplitudes are moved to the matching partials of the new note, partial `n` to partial `n` (the string is fretted elsewhere). `tremolo` 1, or CC 1 at 0.5 or more, repeats the stroke every `1 / tremolo_rate_hz` seconds while the note is held. A note-off (unless CC 64 is at 0.5 or more) multiplies every amplitude of the course by `exp(-dt / 30 ms)` per sample from then on; releasing CC 64 applies this to every course whose note is off. One note sounds per course: `courseForNote` picks the highest-pitched course whose lower open string is at or below the note and within `maxFret` frets (mandolin 24, Greek bouzouki 27, Irish 24).

**D-064 Body.** A body is a list of modes `(f_k, Q_k, g_k)` from `presets/bodies.json`. Its normalised admittance is `Yhat(f) = sum_k g_k (i f/f_k) / (1 - (f/f_k)^2 + i f / (f_k Q_k))` and its bridge admittance `Y(f) = body_coupling * Y_ref * Yhat(f)`, where `Y_ref = 2e-3 * pi * Y0_top / (2 Re Yhat(f_top))` with `f_top` and `Y0_top` the open frequency and wave admittance of the first string of the highest-pitched course: so `eta_b` of that string's fundamental is 2e-3 at `body_coupling` 1 (if `Re Yhat(f_top)` is not positive, `Y_ref = 0`). The bridge force is `F = sum over every partial of every string of Re(a)`. Each mode's velocity obeys `v'' + (w_k/Q_k) v' + w_k^2 v = g_k (w_k/Q_k) F'`, discretised by the bilinear transform; the body output is the sum of the mode velocities plus `F` through a second-order Butterworth high-pass at 1.5 kHz (the modes above the listed ones). The output gain `G_out` of D-013 then applies (calibrated on MIDI 69 for the mandolin and 62 for the bouzouki). With `body_coupling` 0 the strings see a rigid bridge (`Y = 0`) and the body modes are still driven. A `tap` event of strength `s` adds an impulse of height `s * fs / 1000` to `F` and strikes no string; it reaches the engine through the internal header of `S-240`, not through the public interface. Spike S17 shows the two-stage decay of the E pair on the bowl-back (early -95.6 dB/s, late -22.5 dB/s; one string alone -56.5 and -56.6), beats of 1.534 Hz for a 4-cent mistuning on a nearly rigid bridge, and the first three f-hole body modes ringing within 11 dB of each other after a tap.

(D-065 to D-069 are not used. The frozen tests cite the range "D-060 to D-073"; it means D-060 to D-064 and D-070 to D-073.)

**D-053 Listening tools.** `tools/listening/make_blind_pairs.py` and `score_blind.py` are copied unchanged from `qualitycoding/skills` at commit `a20ed73` (Apache-2.0, compatible with AGPL-3.0). Pass condition per gate: no more than 8 of 12 pairs identified correctly, and no demo described by the listener as wrong. **Control pairs (R-011, R-022).** Every round with pairs adds two control pairs, built from the instrument's 13th and 14th references by id, which are not among the 12 real pairs, so no clip of a control repeats a clip of a real pair (for the accordion the two TinySOL control notes of `plan/ENVIRONMENT.md` section 1; for an instrument with fewer than 14 indexed notes, the first two by id, and the gate record says that two control clips repeat real-pair clips, R-071): the reference against a pure sine at the note's equal-tempered fundamental (A4 = the row's `a4_hz` in `sets`, else 440 Hz) carrying the reference's own level envelope (RMS over consecutive 10 ms windows, linearly interpolated between window centres), which no attentive listener takes for the real instrument whatever they think synthetic sounds are like (R-052). The listener receives 14 pairs in one shuffled order and is not told which are controls. A round is void, and is repeated with a new seed without counting towards the round limit, if either control pair is answered wrongly, or if the listener gives one letter for 10 or more of the 14 pairs while the key has fewer than 10 of that letter (side bias is judged against the key, so a listener who answers every pair correctly is never voided). `tools/build_evidence.py` refuses a seed whose 14-pair key puts the real instrument on the same side 10 or more times (exit status 3, printing only 'unbalanced key'); it computes the key from the seed and the 14 stems taken from the index, exactly as the pair builder will, before rendering anything, in every run that would build pairs, including a CI run that builds demos only because a reference is private, so a refused seed is never used for the CI demos; the implementer then uses the next attempt number, and the refused seed counts as no attempt (R-072). Seeds: attempt `k` (0, 1, 2, ...) of round `N` of gate G-L`g` uses seed `1000 * g + 100 * N + k` (`k` below 100; `N` is at most 8 even with `override-round-limit`, since confirmation rounds use the range from 900), so no two gates, rounds or attempts share a key (R-034); its records are `listening/<gate id>-round-<N>-attempt-<k>.md`, and the gate file of the round gains one section per attempt. **Confirmation after a change (R-068).** Every gate record names the commit its evidence was built from. The comparison is made like this: `git worktree add $HOME/folk-gate-<gate id> <gate commit>`, CORE BUILD in that tree into `$HOME/folk-build-<gate id>`, that tree's `tools/build_evidence.py --demos-only` with the gate's seed, the head's with the same seed, and a file-by-file sha256 comparison of the two `demos/` folders (a file present in only one counts as a difference). Confirmation `j` (0 to 9) uses seed `1000 * g + 900 + 10 * j + k` (`k` the attempt, 0 to 9; when `k` would reach 10, or `j` 10, the owner is asked whether to continue; `override-round-limit` never takes `N` past 8; normal rounds stay below `N = 9`, so seeds never collide), records `listening/<gate id>-confirm-<j>-attempt-<k>.md` and a section `Confirmation <j>` in the gate's last gate file, the same questions, the void rules and the pass condition where pairs exist, and the answers `confirm` or `iterate: <notes>`; it does not count towards the round limit. `confirm` closes the gate again if the full pass condition holds (the score where pairs exist, and the answer's `wrong:` line reads `wrong: none` in every case, with or without pairs) or, for a gate closed with `proceed-with-rescope`, if the owner states that the recorded shortfall still describes the result; otherwise the owner may answer `proceed-with-rescope: <text>` (a new rescope, copied into `DEVIATIONS.md`), `iterate` or `stop` (rule DR-15); the gate file's status is `OPEN` from the start of a confirmation round until one of these answers; `iterate` opens the gate's next normal round, which does count towards the limit. After two confirmation rounds of one gate, a third is not started without the owner's answer: `confirm-again` (run the third confirmation round, with listening), `proceed-with-rescope: <text>` (close on the stated shortfall without another round) or `stop`, so confirmations cannot cycle between gates of one family (R-079). After two void attempts in one round the record asks the owner, with the allowed responses `repeat` (another attempt), `proceed-without-pairs: <text>` (the gate is judged on the remarks alone, recorded as a rescope) or `stop`. ## Part 3. Interfaces

**D-090 Core API.** `core/include/folk/engine.h`, `tuning.h`, `strings.h`, as committed. Errors: functions with table arguments throw `std::out_of_range` for an index outside the table; physical formulas throw `std::invalid_argument` for non-positive lengths, diameters, tensions, densities or frequencies and for a partial number below 1; `Engine` methods called on the audio thread never throw: out-of-range notes, controllers, parameter indexes, offsets and non-finite values are ignored or clamped (T-009). `setParam`, `getParam`, `saveState` and `loadState` work on an engine that has never been prepared and allocate only for the text itself; tables and voices are built in `prepare()` (so a temporary engine for state handling, D-094, costs microseconds). `Engine::prepare` may be called again with another rate. It accepts any rate and never throws: from 44 100 to 96 000 Hz the engine plays; at any other rate it produces silence (`process` writes zeros, notes are ignored) until it is prepared at a supported rate again, and the wrapper's editor says so in one line of text (R-020; T-302). `int latencySamples() const` returns the processing latency in host samples (23 for the reed instruments, D-011; 0 for the plucked ones). Events with the same sample offset are applied in the order they were received (the queue is stably ordered by offset). State text: the first line `folk-state 1 <instrument name>`, then one line per parameter in table order, `id=value`, value written with 9 significant digits in the `%.9g` form by a `std::ostringstream` imbued with `std::locale::classic()` (`std::setprecision(9)`, default float format) and read by a `std::istringstream` imbued with `std::locale::classic()` that must consume the whole value (both independent of the process locale and available on every pinned toolchain, including Apple's libc++ at deployment target 11.0, which lacks floating-point `std::to_chars` and `std::from_chars`; never `printf`, `strtod`, `atof` or a stream left on the global locale, which follow the process locale, so that a host running under a decimal-comma locale keeps its sessions: R-017, T-016, T-302), every line ending in `\n`, nothing else; `loadState` accepts a text only if every line is complete and well formed (each key known and given once, each value a finite number); keys may be missing (they keep their current values); a text that fails any of these is refused as a whole and changes nothing.

**D-091 Parameters.** The table in `tests/cpp/param_table.h` is the specification: order, ids, ranges, defaults, step counts. Common: `level`, `a4_hz`. Reeds add `breath`, `breath_source`, `vibrato_rate_hz`, `vibrato_depth`, `air_noise`. Plucked instruments add `pick_position`, `pick_stiffness`, `pair_detune_cents`, `course_mode`, `body_coupling`, `damping`, `tremolo`, `tremolo_rate_hz`, `bend_range`. Then the instrument's own parameters. Each parameter's display name is its id with underscores replaced by spaces, the first letter capitalised, and `hz` written `Hz` (for example `vibrato_rate_hz` is shown as 'Vibrato rate Hz'); the implementer may write better labels as long as none is empty. `breath` is the starting breath for `breath_source` 1 and 2 until the first controller message arrives; with `breath_source` 0 the note velocity is the breath and `breath` is not used.

**D-092 Render tool.**

```
folk-render --instrument <harmonica|accordion|melodion|mandolin|bouzouki> --events <file> --out <file.wav>
            [--sr <44100..96000, default 48000>] [--block <1..8192, default 256>] [--set <id>=<value>]...
folk-render --instrument <name> --list-params
folk-render --instrument <name> --dump-model [--set <id>=<value>]...
folk-render --version | --help
```

- Event file: UTF-8 text, one event per line, `<time in seconds> <kind> <arguments>`; kinds `on <midi> <velocity 0..1>`, `off <midi>`, `cc <number> <value 0..1>`, `bend <-1..1>`, `set <id> <value>`, `tap <strength 0..1>` (plucked instruments; ignored by reeds), `end`. Times never decrease. The last event is `end`; rendering stops there. An end time above 600 s, a negative time, or any time that is not a finite number, is a malformed file (status 3). Blank lines and lines starting with `#` are skipped. A line longer than 1000 characters is an error. A `set` event with an unknown parameter id or a value that is not a finite number is a malformed file (status 3); a finite value outside the parameter's range is clamped, as `setParam` does.
- Output: stereo, 32-bit float WAV at `--sr`, written by the tool's own writer with a plain `fmt ` and `data` chunk (format tag 3) and nothing else: no PEAK chunk, no time stamp, so two runs give identical bytes (C-056). The file is written to a temporary name and renamed, so a failed run leaves no output file.
- `--list-params`: one line per parameter, `id<TAB>min<TAB>max<TAB>default<TAB>steps`.
- `--dump-model`: JSON on standard output. For plucked instruments: `{"scale_length_m", "young_modulus_pa", "max_fret", "courses": [{"strings": [{"midi", "diameter_m", "wound", "linear_density", "core_m", "B"}]}], "body_modes": [{"hz", "q", "gain"}]}` with `B` the inharmonicity of the open string, `diameter_m` the outer diameter and `core_m` the diameter of the steel core (equal for a plain string). For reeds: `{"instrument": "<name>"}`.
- `--version` prints `folk-render <project version>`.
- Exit status: 0 success; 2 usage error (unknown instrument, option or parameter, bad value, rate or block size out of range); 3 malformed event file (the message on standard error names the line as `line <n>`, or says the `end` event is missing); 4 input or output file error.

**D-093 MIDI.** Note-on and note-off; pitch wheel (the melodion ignores it: a keyboard reed instrument with no bend mechanism); CC 1 modulation (vibrato depth for reeds, tremolo switch for plucked instruments); CC 2 and CC 11 breath; CC 64 sustain (plucked instruments); CC 120 and CC 123 all notes off (`allNotesOff`). Other messages are ignored. All channels are merged. Mapping from MIDI to the engine: velocity `v / 127`, controller value `v / 127`, pitch wheel `(v - 8192) / 8192` (T-303).

**D-094 Wrapper.** One source file `plugins/common/FolkProcessor.cpp` (the implementer may add files beside it) compiled once per plugin with `FOLK_INSTRUMENT` defined. It owns a `folk::Engine`; exposes each core parameter as a JUCE parameter with the same id (version hint 1) in the same order, discrete ones as choice or integer parameters; forwards MIDI with sample offsets; copies parameter values to the engine at the start of each block; has no audio input bus and one stereo output bus; reports the engine's `latencySamples()` and `tailSeconds()` to the host; saves state as the state text of a temporary engine, created off the audio thread and given the current JUCE parameter values (a host may save without a block in between, T-302; the live engine is never touched from another thread, and the audio thread takes no lock: parameters cross through atomics; R-021, T-304), followed by one extra line `#program <index>` (the current program, 0-based). On restore the wrapper removes a last line that starts with `#program ` before calling `loadState`; if the rest is accepted it sets the current program to that index without applying it (an index outside the program list, or a missing line, leaves the current program at 0 and records no restored index, so a later `setCurrentProgram(0)` applies preset 0); a text whose only fault is a bad `#program` line is still restored. A state is restored only if `loadState` accepts its engine text, and then the JUCE parameters are updated from the temporary engine; returns an editor that consists of one line of status text (empty, or the unsupported-rate notice of D-090) above a `juce::GenericAudioProcessorEditor` grouped under headings by the implementer's choice of layout (A-008), with the variant presets of `presets/factory.json` exposed as JUCE programs (`getNumPrograms`, `getProgramName`, `setCurrentProgram`), which hosts show as their preset menu; a custom editor component is not required. `setCurrentProgram(i)` may be called on any thread, including the audio thread: it only writes the preset's values with `AudioProcessorParameter::setValue` (an atomic store; no `setValueNotifyingHost`, which calls into the host) and asks the message thread, through a lock-free flag polled by a timer, to call `sendValueChangedMessageToListeners(getValue())` on each parameter of the preset (so the editor and the VST3 wrapper's cached values follow) and then `updateHostDisplay(juce::AudioProcessorListener::ChangeDetails().withProgramChanged(true))`; it never touches the engine, allocates or locks; it applies preset `i` unless `i` is the index set by the last `setStateInformation` and no other program has been selected since, in which case it does nothing; so a fresh instance applies any program chosen, including program 0, while a host that re-selects the restored program after loading a session changes nothing; a restore itself never applies a program (R-018, T-302). The wrapper maps MIDI by D-093 and splits a block larger than the prepared size into chunks; its output equals the core's for the same events and parameter values (T-303). ## Part 4. Decision rules

The default rule for anything not listed: choose the most reversible option that does not expand scope, log it in `DEVIATIONS.md` with the reason, and continue, unless it touches frozen tests, security, data integrity, a public interface (Part 3) or research integrity, in which case halt and write `BLOCKED.md`.

| ID | If | Then |
|---|---|---|
| DR-01 | A dependency fetch fails (git clone of JUCE or Catch2, pip install, pluginval download) | Retry 3 times with 30 s, 60 s, 120 s waits. If it still fails locally but succeeds in CI, record the step as "blocked locally, verified in CI" with the run URL. If it fails in CI too, halt with `BLOCKED.md`. Never change a pin to make a fetch succeed. |
| DR-02 | A pinned version has been withdrawn or a runner label has been retired | Halt with `BLOCKED.md` naming the pin, the evidence and the nearest replacement; the planner amends `plan/ENVIRONMENT.md`.
