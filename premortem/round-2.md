## Incident report (simulated, 16 May 2027)

The pull request merged on 2026-12-18. Every `Done when` was met: 27 Catch2 cases, two locale cases, 316 Python tests, 7 of 7 host tests on four runners, `host-tsan` green, 20 pluginval logs, T-013 at 4.2 times real time, and all five listening gates closed.

By May the owner had stopped using the plugins. Three things went wrong, each through a check that round 1 had added.

**Lost sounds.** The owner picked the factory preset "Violin, Scottish" in Live, adjusted it, and saved the set. When it reopened, the sound was the bare factory preset. The wrapper wrote `#program 0` every time, because `setCurrentProgram` applied a preset but never stored its index. Live then re-applied program 6 after the restore, and the wrapper treated that as a new selection. The frozen test meant to stop this (T-302, "re-selecting the current program") saves and restores only at program 0, so it passes whether or not the program is stored.

**Intermittent dropouts.** The accordion dropped out whenever Live autosaved during playback. The first `host-tsan` run had reported races inside JUCE's start-up code. The implementer added `race:juce::*` to `tests/ci/tsan.supp`, a file that is not frozen, and logged the deviation as the plan asks. That one line also hid a race in the wrapper, where a structural parameter was handed over from `setStateInformation`. No test can see the mutex added later to "fix" a crash report, because ThreadSanitizer does not flag locks.

**A listening record that does not mean what it says.** In round 1 the owner failed a control pair twice. Asked "which side is the real instrument", they chose the low-passed recording, reasoning that synthetic sounds are too bright. After two void attempts, D-053 offered `proceed-without-pairs`, which `plan/GATES.md` does not list as an allowed response. The implementer recorded it as a rescope, so G-L3 was decided on remarks alone. The mandolin's round-1 key turned out to equal the accordion's, letter for letter, because the key depends only on the seed and the number of pairs.

The G-L1 question 4 fix for the pitch wheel, and the reed changes from two `iterate` rounds, landed after `S-REVIEW` and `S-ADVERSARIAL`. No reviewer saw them. The pull request linked the earlier reviews as if they covered the delivered code.

No step was skipped. The round-1 mitigations were present, but each one could pass without doing its job.

## Findings by lens

### 1. Technical correctness (DSP, numerics, real-time safety, state, the tests themselves)

- **F-1 (residual on R-018, Critical, plausible). The program test cannot fail.** `T-302 re-selecting the current program after a restore changes nothing` never selects a program before saving. Both instances therefore sit at program 0, and `CHECK(b->getCurrentProgram() == a->getCurrentProgram())` holds whether or not the `#program` line is written, parsed or applied. The natural bug (`setCurrentProgram(i)` applies the preset but never stores `i`) is invisible to the test. The R-018 harm follows in any host that re-applies the saved program after a restore.
- **F-2 (residual on R-021, High, plausible). `host-tsan` can be silenced, and it cannot see locks.** Three gaps:
  - The workflow uses `tests/ci/tsan.supp` if it exists. The file is not in the frozen manifest, and its content is restricted only by prose in ENVIRONMENT section 5 ("every frame lies in JUCE module code").
  - A TSan `race:` pattern suppresses a report if it matches any frame of either stack. So a pattern written for a JUCE-internal report, such as `race:juce::`, also suppresses wrapper races whose stacks pass through JUCE code.
  - There is no positive control showing that the build is instrumented, and T-304 asserts only finiteness and counts. A lock taken on the audio thread, which D-094 forbids, is invisible to ThreadSanitizer and to every test.
- **F-8 (new, Medium, plausible). Moisture runs the reed far outside its tested range.** D-040's `moisture` adds `0.4 * x0` to `hmin`, which is a factor of about 5.2 on `hmin` at moisture 1, and scales `Q` down to 0.1. D-012's calibrated range is 1 to 2 on `hmin` and 0.5 to 2 on `Q`, and C-063 shows that a factor of 0.3 on `Q` already silences the reed from rest. T-132 accepts "at least 6 dB quieter", so silence or a D-015 reset (divergence) passes. No check runs `reed_probe` at the five moisture tables.
- **F-16 (new, Medium, remote). A program change can arrive on the audio thread.** In VST3, JUCE exposes the programs as a program-change parameter, and a host can deliver changes to it within `process`. Applying a preset there (parsing `factory.json` data, building a temporary engine, notifying the host for each parameter) would allocate on the audio thread. T-011 covers the core only, and T-304 never calls `setCurrentProgram`.
- **Speculative (F-15).** libc++ `num_get` sets `failbit` when `strtold` reports `ERANGE`, which includes subnormal results. A state value that is subnormal would be refused on macOS. I found no path to a subnormal value: parameters are clamped, and normalised automation does not produce one.
- R-017's mitigation looks effective. T-016 and the T-302 locale case use `setlocale`, which catches the `printf` and `strtod` route that D-090 bans. R-020 is restated: T-302 does not assert the silence D-090 prescribes, but D-090 is explicit. R-019 is restated: T-303 covers mapping and chunking at processor level, and the VST3 layer remains pluginval's and G-L1 question 4's.

### 2. Dependency and supply-chain drift

- **F-5 (new, Critical, remote). A cache hit skips every integrity check on TinySOL.** On a hit, the TinySOL download step, and with it the md5 check, is skipped in both workflows. Only the file count (689) and the metadata md5 are checked after that. T-200 measures about 100 accordion files that nothing hashes, and `fetch_references.py` re-checks only the 12 indexed rows. A cache entry written by a run whose dependency chain was compromised (any job on the same branch may create the key on a miss) feeds T-200 altered reference data, and it passes silently.
- The hash-locked installs, SHA-pinned actions, hash-checked pluginval, `persist-credentials: false` and the split `gate-evidence` workflow look effective (R-030). The publish job trusts the evidence job's `gate` output, but `git` rejects any value that would escape `evidence/`. `pip-audit==2.10.0` is installed unhashed in a read-only job: Low, not registered.
- Restated: R-028 (post-delivery drift; add T-013's thin margin on a changed runner CPU class to its list), R-006.

### 5. Integrity

- **F-3 (continued).** The control pair is "reference against the reference low-passed at 2 kHz", and the question is "which side is the real instrument". Both sides are real recordings. An attentive listener who believes synthesis sounds too bright will choose the dull side, so the control measures the listener's theory, not their attention. Voids follow, then `proceed-without-pairs`, and the gate is decided without pairs: the harm R-022 was meant to remove.
- **F-4 (new, High, plausible). Code changed after review ships unreviewed.** `S-REVIEW` and `S-ADVERSARIAL` precede `S-LISTEN`. DR-12 `iterate` rounds (up to 3 per gate, 5 gates), G-L1 question 4 defect fixes in the wrapper (state, MIDI, threading) and the merge of `origin/main` in S-INTEGRATE all change code afterwards. Only the frozen suite is re-run. The pull request links `reviews/CODE_REVIEW.md` and `ADVERSARIAL_REVIEW.md` as the review of the delivered code.
- **F-6 (residual on R-034, Medium, plausible). The answer key is the same for every gate.** `make_blind_pairs.py` draws `rng.sample(stems, 14)` and then one `rng.random()` per pair, so the A/B key depends only on the seed and the number of pairs, not on the instrument. I ran the simulation: seed 10 gives `ABBAAAAABAAAAA` for all five gates, seed 20 gives `ABAABBAABBAAAA`, and seed 11 gives `ABBBBAABBBBAAB`. D-053 fixes the seeds publicly. S-LISTEN action 5 commits each decoded score and controls, and the five gates may be open together. Once one gate's key is known, every other gate's key for that round is known, and with it where the controls sit for instruments whose stems sort the same way. That breaks HANDOFF section 9 ("a new seed after every round whose results the listener has been told") across gates, and lets a careless listener pass the controls.
- **F-7 (new, Medium, plausible). Staleness checks never run after S-300.** `gen_presets.py --check` and `calibrate_reeds.py --check` are not in CI. They run in S-300 and in each S-330 round, but not after a DR-12 `iterate` change or a merge from `main`. A stale `presets_data.h` builds and passes, because CI uses the committed header and never regenerates it. Stale reed offsets also pass while the error stays below T-100's 5-cent tolerance. The delivered binary then no longer matches the committed calibration data.
